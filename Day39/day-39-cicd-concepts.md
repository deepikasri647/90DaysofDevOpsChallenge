## 🚨 Task 1: The Problem with Manual Deployments

When multiple developers continuously push code to a shared repository and manually deploy directly to production, several severe bottlenecks occur:

1. **"It Works on My Machine" Syndrome:** Discrepancies between local development environments (different OS versions, missing environment variables, conflicting dependencies) cause code that passed locally to crash instantly in production.
2. **Merge Hell:** Integrating code changes manually once every few weeks results in massive code conflicts that take days to resolve.
3. **High Deployment Risk & Slow Release Velocity:** Teams deploying manually can safely release software only once every few weeks during late-night maintenance windows due to high human error risk during manual testing, building, and copying binaries.

## 🔄 Task 2: CI vs. CD vs. CD Comparison

| Practice | Core Focus | Trigger / Execution | Human Gate Required? | Real-World Example |
| --- | --- | --- | --- | --- |
| **Continuous Integration (CI)** | Automatically building, linting, and running unit/integration tests on every code commit. | Triggered automatically on `git push` or `pull_request`. | No | Developers merge a Pull Request; a test runner executes automated test suites to ensure zero breaking changes. |
| **Continuous Delivery (CD)** | Automatically packaging application artifacts (Docker images, binaries) and deploying to **Staging/QA** environments, keeping the codebase in a **release-ready state**. | Automated builds; final push to Production requires manual approval. | **Yes** (Manual Approval for Production) | A fintech app automatically deploys every passed build to a Staging server, requiring the QA lead to click "Approve Release" for Production. |
| **Continuous Deployment (CD)** | Fully automated pipeline where every change that passes all tests automatically deploys straight to **Production** with zero human intervention. | 100% Automated end-to-end. | **No** | SaaS platforms (e.g., Netflix, GitHub) automatically pushing hundreds of microservice updates to production daily after passing automated canary testing. |

## 🏗️ Task 3: Anatomy of a CI/CD Pipeline

* **Trigger:** The event that initiates pipeline execution (e.g., `git push`, `pull_request`, schedule/cron, or manual dispatch).
* **Stage:** A logical grouping of tasks executed in sequence (e.g., `Build` ➔ `Test` ➔ `Package` ➔ `Deploy`).
* **Job:** A set of steps executed on the same runner environment. Jobs within a stage run in parallel by default unless configured with dependencies.
* **Step:** An individual task or command executed sequentially inside a job (e.g., running `npm install` or `docker build`).
* **Runner:** The physical machine, virtual machine, or Docker container that executes pipeline commands (e.g., GitHub-hosted `ubuntu-latest` or self-hosted runners).
* **Artifact:** The output file, compiled binary, or container image generated by a build job and passed to subsequent deployment stages (e.g., `.tar.gz`, `app.jar`, or Docker image).
